# Технический отчёт: Interview Assistant

Дата анализа: 12 июля 2026 г.  
Область: весь каталог проекта (14 Python-файлов, 3 966 строк), конфигурация, документация и системный prompt.  
Метод: статический анализ исходного кода, сверка документации с реализацией, компиляция Python-модулей и проверка доступности зависимостей. Полноценный запуск не выполнялся: в текущем окружении отсутствуют `mss`, `pyaudio` и `pynput`, а приложение требует Windows-аудиоустройство и запущенный LM Studio.

## 1. Техническое резюме

Проект задуман как локальный Windows-помощник для технических интервью в реальном времени. Он должен захватывать системный звук, транскрибировать речь через faster-whisper, распознавать вопросы и просьбы написать код, периодически снимать экран, передавать текст и изображения локальной мультимодальной модели через OpenAI-совместимый API LM Studio и выводить краткую подсказку в поверхностном PyQt6-окне.

Архитектурная идея понятна, компоненты хорошо разделены, а исходники синтаксически корректны. Однако текущая версия находится на уровне прототипа и не готова к надёжному использованию: основной сценарий запуска содержит блокирующие дефекты, часть заявленных оптимизаций не подключена, несколько настроек игнорируются, автоматических тестов нет. Наиболее вероятный фактический результат запуска — авария при создании `OverlayWindow` до `QApplication`; даже после исправления запуск без сохранения скриншотов ломается в коде временного файла, а горячая клавиша паузы обращается к отсутствующим методам аудиозахвата.

Итоговая оценка зрелости: **функциональный прототип / pre-alpha**. Концепция и модульность пригодны для дальнейшей разработки, но эксплуатационная готовность низкая.

## 2. Назначение и целевой сценарий

Основной пользовательский сценарий:

1. Пользователь запускает LM Studio с мультимодальной моделью и затем `main.py` либо `main_optimized.py`.
2. Приложение захватывает звук выбранного входа или найденного loopback-устройства.
3. Каждые примерно 3 секунды накопленный PCM-фрагмент передаётся faster-whisper с фиксированным русским языком.
4. Регулярные выражения определяют вопрос или запрос на написание кода.
5. При событии агрегируются последние 30 секунд текста, до двух последних скриншотов и до пяти событий.
6. Контекст отправляется на `http://localhost:1234/v1/chat/completions`.
7. Ответ отображается в always-on-top overlay; глобальные hotkeys переключают быстрый режим, паузу и принудительный запрос.

Продукт ориентирован не на подготовку к интервью, а на скрытую помощь непосредственно во время интервью. Это создаёт этические, договорные и privacy-риски: запись чужой речи и экрана может требовать согласия участников, а скрытое использование может нарушать правила интервью или работодателя. Такие ограничения следует явно отразить в интерфейсе и документации.

## 3. Реальная архитектура

| Компонент | Роль | Состояние |
|---|---|---|
| `main.py` | Базовая оркестрация | Дублирует optimized-версию; содержит те же критические проблемы запуска |
| `main_optimized.py` | Оркестрация с cache/debounce и CLI hotkeys | Предполагаемая основная версия, но async/streaming не подключены |
| `audio_capture.py` | PyAudio-захват mono Int16, поиск loopback по имени | Реализован, но это не полноценный WASAPI loopback API; pause/resume отсутствуют |
| `transcriber.py` | Очередь аудио и faster-whisper | Реализован; частота 16 kHz и окно 3 сек жёстко зашиты |
| `question_detector.py` | Regex-классификация вопросов и code requests | Работает только по ограниченным шаблонам; LLM-классификации нет |
| `screen_capture.py` | Снимок всех мониторов, normal/fast mode | Есть критический дефект временного сохранения и риск конкуренции потоков |
| `context_aggregator.py` | Склейка текста, событий и скриншотов | Простая и понятная реализация; speaker фактически всегда interviewer |
| `multimodal_client*.py` | OpenAI-совместимые запросы к LM Studio | Базовый sync-клиент; optimized добавляет cache, debounce, stream и executor |
| `overlay_gui.py` | PyQt6 always-on-top окно | Не гарантирует скрытие из screen sharing; GUI вызывается из фоновых потоков |
| `hotkeys.py` | Глобальные комбинации через pynput | Валидация и CLI override реализованы |
| `performance_monitor.py` | Метрики и советы | Изолирован и нигде не подключён |

Потоки данных:

`PyAudio callback → audio queue → Whisper worker → detector → context → LM Studio HTTP → overlay`

Параллельно работает `screen capture worker → JPEG path → context`, а `pynput` вызывает управляющие callbacks из собственного потока.

## 4. Реализованный функционал

- Захват mono PCM через PyAudio и эвристический поиск устройства по словам `loopback`, `stereo mix`, `what u hear`.
- Локальная транскрипция faster-whisper с VAD и русским языком.
- Regex-детекция русских и английских вопросов и запросов на код.
- Периодический захват всех мониторов, JPEG-компрессия и два интервала работы.
- Контекстное окно текста, событий и двух последних изображений.
- OpenAI-compatible multimodal message с base64 data URL.
- Локальный HTTP-клиент LM Studio с историей последних сообщений.
- Overlay с форматированием HTML, статусом и уведомлениями.
- Глобальные hotkeys и CLI-переопределение hotkeys в optimized-версии.
- В optimized-клиенте отдельно реализованы TTL-cache, дедупликация, streaming и executor API.

## 5. Критические и существенные дефекты

### P0 — приложение создаёт QWidget до QApplication

`initialize_components()` создаёт `OverlayWindow`, а `QApplication` создаётся только после возврата из этой функции (`main_optimized.py:225–228`, `399–410`; аналогично в `main.py`). Для Qt это недопустимый порядок и обычно приводит к `QWidget: Must construct a QApplication before a QWidget`.

Решение: создать единственный `QApplication` в `main()` до создания `InterviewAssistant`/overlay и передать его жизненный цикл оркестратору.

### P0 — стандартный режим временного скриншота неисправен

При `save_screenshots: false` вызывается `mss.tools.to_png(data, 0)`, хотя `data` уже является JPEG, а второй аргумент должен описывать размер raw-буфера (`screen_capture.py:163–195`). Ветка fallback практически недостижима, потому что наличие функции проверяется, но исключение не перехватывается. По умолчанию это ломает первый снимок и все мультимодальные запросы.

Решение: использовать `tempfile.TemporaryDirectory`/`NamedTemporaryFile`, напрямую записывать JPEG-байты и управлять удалением файлов.

### P0 — пауза аудио не реализована

Оркестраторы вызывают `self.audio_capture.pause()` и `.resume()`, но в `AudioCapture` таких методов нет. Hotkey паузы завершится `AttributeError`; pynput его залогирует, но состояние `is_paused` уже переключится, оставив систему в непоследовательном состоянии.

### P1 — GUI небезопасно обновляется из фоновых потоков

Транскрипция выполняет callback из worker-потока, hotkeys — из listener-потока; оба пути напрямую вызывают методы PyQt widgets и `QTimer.singleShot`. Qt требует обновлять GUI в главном потоке. Возможны случайные падения, предупреждения таймеров и гонки состояния.

Решение: определить Qt signals/slots или thread-safe очередь, которую читает `QTimer` главного потока.

### P1 — «optimized» версия не использует async и streaming

`main_optimized.py:302–327` напрямую вызывает синхронный `chat()`. Методы `chat_async()` и `chat_stream()` существуют, но в приложении не используются, несмотря на лог `Асинхронные запросы к LMStudio`. До 120 секунд HTTP-ожидания блокируют transcriber callback и задерживают обработку следующих транскрипций.

### P1 — overlay не скрыт от демонстрации экрана

`Qt.Tool`/`WS_EX_TOOLWINDOW` скрывает окно из Alt+Tab/taskbar, но не исключает его из screen capture. В коде нет `SetWindowDisplayAffinity(..., WDA_EXCLUDEFROMCAPTURE)`. Более того, собственный `mss`-захват всех мониторов также может включить overlay. Заявление README о невидимости при демонстрации не подтверждено реализацией.

### P1 — остановка после частичной ошибки не очищает ресурсы

`stop()` сразу возвращается при `is_running == False`; этот флаг ставится только после запуска всех компонентов. Ошибка посередине инициализации/старта может оставить PyAudio, mss, notification setting или executor неосвобождёнными.

### P1 — захват экрана потенциально использует mss из разных потоков

Один объект `mss.mss()` создаётся при инициализации, используется capture-thread и может одновременно использоваться hotkey/transcriber-потоком через `force_capture()`. Это не защищено lock и создаётся не обязательно в том потоке, где вызывается.

### P2 — конфигурация частично не работает

- `logging.save_screenshots` объявлен в YAML, но код ищет `screen.save_screenshots`.
- `logging.save_transcripts` нигде не используется.
- `lmstudio.api_endpoint`, `model.name`, `model.quantization` игнорируются; в запросе всегда `model: local-model`.
- `model.cache_enabled` и `cache_size` из документа оптимизаций игнорируются; cache принудительно включён с размером 100.
- `ScreenCapture.max_buffer_size` жёстко равен 5, хотя агрегатор получает настройку.
- transcriber рассчитывает длительность через фиксированные 16 kHz и всегда собирает ровно 3 секунды, независимо от `audio.sample_rate` и `buffer_duration`.
- logging level читается через `getattr(logging, value)` без явной валидации.

### P2 — метрики cache статистически неверны

Оркестратор читает несуществующий `_cache_hits`; optimized-клиент его не увеличивает. Поле статистики либо всегда ноль, либо логика считает накопленный счётчик как новый hit на каждом последующем запросе, если поле когда-либо появится.

### P2 — детектор значительно уже заявленного

Docstring обещает `NLP паттерны + LLM классификацию`, но есть только regex/substring. Обычные вопросы с вопросительным знаком без известных формулировок не определяются; один regex-match даёт confidence 0.65 и при стандартном threshold 0.7 отбрасывается. Поэтому многие естественные вопросы никогда не вызовут ответ.

### P2 — контекст не различает говорящих

Каждая транскрипция добавляется как `interviewer`; микрофон кандидата отдельно не захватывается и speaker diarization отсутствует. Модель получает не «диалог», а один поток системного аудио с предположением об авторе.

### P2 — файлы и история не имеют корректного lifecycle

Пути удалённых из буфера скриншотов не удаляются с диска; timestamp имеет точность одну секунду, поэтому параллельные/повторные captures могут перезаписывать файл. `clear_buffer()` также не удаляет файлы. История LM-клиента ограничивается только при чтении последних 10 сообщений, но в памяти растёт без ограничения до завершения сессии.

## 6. Качество, безопасность и эксплуатация

Положительные стороны:

- Компоненты разделены по ответственности и имеют type hints/docstrings.
- HTTP-запросы имеют timeout и `raise_for_status()`.
- Cache защищён lock; ключ включает содержимое изображений.
- Очереди имеют лимиты, что сдерживает неконтролируемый рост памяти.
- Приложение ориентировано на локальную модель, поэтому данные не обязаны уходить во внешний SaaS.

Риски:

- Проект захватывает весь экран и звук; нет consent flow, redaction, allowlist окон или предупреждения о секретах.
- Скриншоты передаются как base64 и могут содержать пароли, токены, личные сообщения и данные других клиентов.
- При локальном сохранении нет шифрования, retention policy и гарантированного удаления.
- Подавление notification sound меняет пользовательский реестр; код не читает исходное значение и «восстанавливает» его как `1`, что может менять пользовательскую настройку.
- Нет package lock/constraints, лицензии как отдельного файла, CI, тестов, telemetry opt-in или health diagnostics.
- README обещает MIT, но в репозитории нет `LICENSE`.

## 7. Проверки и ограничения анализа

Выполнено:

- `python -m compileall -q .` — успешно, синтаксических ошибок нет.
- Поиск тестов — тестовых файлов нет.
- Проверка импортов текущего интерпретатора: доступны `yaml`, `requests`, `numpy`, `PIL`, `faster_whisper`, `PyQt6`, `win32gui`; отсутствуют `mss`, `pyaudio`, `pynput`.
- Git-история недоступна: каталог не является Git-репозиторием.

Не выполнено:

- end-to-end запуск с физическим/loopback аудио;
- загрузка Whisper-модели;
- запрос к реальному LM Studio;
- визуальная проверка overlay и screen-sharing exclusion;
- измерение latency/CPU/GPU/VRAM.

Следовательно, выводы о дефектах основаны на прямых путях исполнения и API-контрактах, а не на полном динамическом прогоне.

## 8. Приоритетный план развития

### Этап 1 — сделать базовый сценарий запускаемым

1. Исправить lifecycle `QApplication` и гарантированную cleanup-машину состояний.
2. Переписать временное хранение скриншотов через `tempfile`, добавить lock и удаление.
3. Реализовать `AudioCapture.pause/resume` или убрать эти вызовы в пользу единого state gate.
4. Перевести все GUI-обновления на Qt signals/slots.
5. Подключить `chat_async`/streaming к UI и запретить параллельные stale responses.

### Этап 2 — добиться корректности

1. Ввести typed config/schema и проверить каждую настройку на фактическое использование.
2. Передавать sample rate/buffer duration в transcriber без hardcode.
3. Добавить автоматическое выключение fast mode и более надёжный detector.
4. Исправить cache/debounce semantics: force request должен обходить и debounce, статистика должна приходить из клиента.
5. Добавить unit-тесты detector/cache/context/config и integration-тест с mock LM Studio.

### Этап 3 — privacy и production readiness

1. Добавить явное согласие, режим выбора окна/области, redaction и понятную индикацию записи.
2. Реально исключить overlay из capture через поддерживаемый Windows API и проверить поведение в Teams/Zoom/Meet; не обещать универсальную невидимость.
3. Ввести управляемый retention и безопасное удаление временных данных.
4. Добавить structured logging без транскриптов/изображений по умолчанию, health screen и диагностику устройств.
5. Устранить две расходящиеся точки входа: оставить один application core и включаемые feature flags.

## 9. Итог

Проект имеет ясную продуктовую идею и разумное разбиение на модули, а optimized-клиент содержит полезные заготовки для cache, streaming и background execution. Но документация заметно опережает интеграцию: ключевые возможности либо не подключены, либо реализованы не так, как заявлено. До использования необходимо устранить как минимум четыре системных класса проблем: lifecycle Qt, временные скриншоты, pause/audio API и межпоточные GUI-вызовы. После этого нужны тесты реального аудиотракта и LM Studio, а затем отдельная работа по privacy, согласию и корректному позиционированию продукта.
